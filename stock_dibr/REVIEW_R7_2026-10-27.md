# R7 implementation review — 2026-10-27

## R6 headset feedback

The user's R6 headset test is negative feedback, not acceptance. Automatic depth
selection produced an image, but the displayed physical candidate ID changed
more than once per second. Manually selected IDs did not provide a reliable
choice. Strength 2.0 looked like reduced world scale; the user prefers 1.0.
Near-character artifacts remained, and the previous isolated-spike repair did
not improve them.

The R6 behavior is consistent with its source: candidate IDs mapped directly to
physical D3D resource identities, manual selection filtered by that exact ID,
and Auto chose largest area then newest serial without hysteresis. A rotating
pool could therefore make an exact manual ID unavailable while another
allocation from the same logical stream was active.

## R7 source changes

The R7 visibility shader, pipeline integration, and UI stages are now present
and applied to the local `backend-r7` tree. The R7 stage order follows the R6
inspector shader and UI. The R6 shader still copies the capture headers before
R7 stages run.

### Producer-pattern grouping and Auto behavior

R7 stores bounded physical members separately from heuristic producer-pattern
IDs. Membership requires a compatible executed producer route, including
producer queue, storage-format family, layout, list position/ordinal, and the
actual executed viewport, plus one corroborating marker: the same executed DSV
descriptor handle or an exact matching nonzero resource debug-name hash.
Physical IDs, route shape, and ordinal alone are not enough to merge resources.
These markers can be shared by unrelated passes or recycled; they are explicit
pattern pins, not unique camera proof. If a marker is absent or conflicts,
members remain separate or the route is marked ambiguous; ambiguous patterns
cannot be manually selected. Unnamed resources with rotating DSV handles may
remain separate physical candidates and unavailable for manual family
selection. The UI warns about this limitation. Grouping does not establish
semantic camera identity or prove depth/color camera provenance.

Auto's initial winner follows the R6 largest-area/latest-sequence policy. Once
chosen, it holds that choice indefinitely while fresh and valid. A larger
resource alone never changes the choice. Auto replaces the choice only after it
is absent or invalid for three consecutive epochs. During that grace period,
Auto may acquire a fresh current-frame physical fallback; it never uses a
previous-frame slot. Manual pattern selection stays pinned and fails closed
when no fresh matching physical member is present. A 150-epoch policy test
checks that a larger resource does not evict a fresh choice. The portable
policy tests reported zero failures. Windows WARP and headset verification
remain pending.

### Visibility-aware reconstruction

The new selectable reconstruction mode defaults to Visibility aware; R6 inverse
reconstruction remains available for comparison. R7 projects source pixels
using current-frame depth, clears per-eye R32_UINT visibility-depth and
source-index maps, scatters projected depth, then selects the source index for
the nearest target depth. The maps provide an actual current-frame coverage
map. The path uses no temporal color or depth history.

Bounded fill defaults to 32 pixels, is capped at 64, and radius zero disables
it. A disocclusion fill requires a small hole, visible samples on both sides, a
depth discontinuity at the boundaries, and a stable farther-background run.
Only a visible farther sample is repeated into the hole. The coverage inspector
uses green for covered pixels, cyan for bounded fill, red for unresolved pixels
that use the R6 geometric fallback, and purple when visibility is unavailable.
Inspector views 1–5 and reconstruction mode 0 preserve the R6 views and path.

Visibility support, pipeline creation, or scratch-allocation failure is
optional: the current frame falls back to R6 and the UI reports the failure
reason. That fallback is implemented but has not yet been verified by the
Windows null-UAV test. Forward warping cannot reveal hidden surfaces, recover
missing geometry, or establish camera provenance. It is not a promised fix for
near-character artifacts caused by incorrect or incomplete input depth.

## Workflow and test scope

The workflow preserves the existing source pins, R5 stage order, test/build
steps, compatibility targets, frontend checks, and package order. It applies
R7 visibility shader, visibility pipeline, and stable-depth UI after both R6
stages and before the existing test step.

`run_tests.py` now records these Windows-only test-scope fields:

- `r7_visibility_analytic_oracles`
- `stable_named_depth_rotation`
- `legacy_null_visibility_uav_fallback`

The local portable policy tests reported zero failures. The local Linux scope
does not execute the WARP tests. `run_tests.py` records the new Windows-only R7
visibility analytic oracles, stable named-depth rotation, and legacy null
visibility-UAV fallback in `test-scope.json`. A Windows workflow run is still
needed for the GPU tests, pinned backend build, compatibility suite, and
installable package. No R7 headset result or acceptance is claimed.
