# Future roadmap review — Luna Max

## Baseline and evidence boundary

This review is for the future branch at Build 46 source `af215afd3a0a624d9c1878e96e836fa9fbf26a4d`. Windows run `39687797421` passed, including all 60 CTests and frontend checks. The extracted inner package SHA-256 is `a7a7b4600b2c20d18f82ff5ae226b29771449f21e39c6a97d5151f5f7c8c361e`. A green production build and component suite still do not establish headset output, lighting parity, queue/fence assumptions, frame pacing, or a performance gain.

Keep the accepted Build 40/ID6 behavior and FOV/gaze/crop baseline intact. ID7 has four independent sources and four full-atlas color allocations per the current design. Its nominal raster area is an estimate, not measured GPU time. All future work below is measurement-led; none of it should be reported as a speedup until a repeatable same-scene headset comparison confirms it.

## Prioritized roadmap

### 1. First increment: on-demand, read-only delivery snapshots

Keep the first code increment bounded to scalar snapshots added to the existing hook-provenance JSON export. Its Debug-page panel is already default-off and exposes refresh/export, including for ID7, so no new UI or per-frame logging is needed. Sample Delivery, NativeDelivery, RHI queued-owner-map sizes, and retirement independently. Every sample reports its own generation where applicable and a busy/unknown state; they are not one coherent cross-ledger instant.

Delivery reports live source slots, incomplete source slots, pending engine tickets, and the existing overflow latch. NativeDelivery reports occupied slots, live tails, shared (including multiple roles on one ticket) and ambiguous tails, plus the oldest retained generation/serial with rendered/hooked/executed/written masks, four pending counts, and completion/publication state. Reporting a retained fully executed slot helps expose owners held after the callback masks are complete. The RHI helper only try-locks its existing vtable mutex long enough to read scalar map sizes, releases it before any ledger snapshot, and never enumerates entries. Retirement uses a try-lock and bounded walks capped at 256 nodes per list, with lower-bound counts and a truncation flag. It reports cached successful-signal and last-poll fence/device/queue identities and values only; export must not query a fence or acquire COM ownership. `UINT64_MAX` is labeled device-removed, not complete. A queue identity observation does not prove producer ordering.

No snapshot retains a packet, command, shared pointer, or COM object; no new sampler, fence, wait, owner, acceptance rule, retirement decision, or timeout is introduced. Empty retirement state means “not observed.” Snapshot busy/drop behavior must not affect selection, drainage, or the overflow latch. Add only the approved short-circuit that skips the existing queue `GetDevice` query when no staged owner exists; keep in-flight polling, pending append timing, and signal behavior unchanged. Tests cover empty/partial/full/reset, shared/quarantined tails, overflow, busy try-locks, snapshot noninterference, bounded list cycles/truncation, independent fence identities, and device-removed formatting. Keep ID6 behavior unchanged.

### 2. Establish a usable performance baseline

Before changing atlas dimensions, source count, or resolution, capture a fixed route and scene on the target headset in native stereo, accepted ID6, and ID7. Record game-thread, render-thread, and GPU scene time separately, delivered and reprojected frame statistics when the runtime exposes them, compositor time, peak VRAM, and the mode’s effective internal screen percentage. Compare a stable interior, a shadowed scene, a high-motion segment, loading, and a repeated mode transition. Hold game settings, HMD refresh rate, runtime, and reprojection/frame-generation settings constant.

Build 46’s `gpu_timing` timer is explicitly scoped to the compositor command pass. It excludes Unreal’s source renders and source gathering, so it cannot drive a scene-resolution controller or substantiate total-render performance. OpenXR wait/begin/end timings are CPU-side scheduling/wait observations, not GPU scene time. Instrumentation for adaptation must cover the actual UE rendering work for one admitted draw and identify whether all of its views executed on the measured queue. For ID6 it must include both source passes; for ID7 it must include all four. If the production hook cannot produce that proof, adaptive control remains unavailable and the timing UI must say so.

### 3. Off-by-default adaptive primary screen percentage for DuoView and QuadView

Use Unreal’s primary internal screen percentage (`r.ScreenPercentage`) as the single adaptation variable. Do not resize the OpenXR/HMD output target (`xr.SecondaryScreenPercentage.HMDRenderTarget`), alter gaze crops, or change ID7’s context/focus layout to imitate screen-percentage adaptation. Primary screen percentage scales internal scene rendering before final output; Epic documents that it can change image quality and that temporal upsampling affects how such changes appear. The exact UE5.5, DX12, STALKER 2 upscaler path must still be verified in-game.

First check whether Unreal’s built-in dynamic-resolution path is supported and correctly wired for this UE5.5 Windows/DX12/OpenXR game and for these deferred view-family renders. Do not assume support from a CVar’s presence: Epic’s current documentation describes dynamic resolution as a pluggable heuristic and documents platform/status gates, while desktop support and behavior vary by engine/platform. If the game’s path is supported, prefer its native screen-percentage driver and verify its actual applied value across every view. If it is unsupported or does not control these view families consistently, use a small custom controller only after the valid whole-scene GPU timing path above exists.

Keep the first custom controller simple and opt-in. Add one shared “Adaptive internal screen percentage” toggle, target frame-time control defaulting to 25 ms (40 rendered scene frames/s), and min/max controls. Start from the user’s current `r.ScreenPercentage`; derive the safe interval from the intersection of actual user limits, title/backend limits, and the active upscaler’s verified source-size bounds. Do not impose a generic 50% minimum or use CVarManager’s 10–150 UI range as a tested adaptive range. Cap the adaptive maximum at the captured baseline unless the user explicitly requests a higher bound. The controller reports scene render time and effective screen percentage separately from the headset’s 120 Hz display/compositor cadence. A 40 FPS scene budget does not mean a 40 Hz headset presentation target.

The controller consumes only recent, complete, frame-matched GPU samples that cover the whole two-view or four-view scene. Use a bounded query ring and delayed readback; associate each result with draw serial, mode, generation, view mask, queue identity, and settings revision. Reject missing/stale samples, incomplete view masks, loading or mode-transition draws, paused/non-viewport frames, invalid timestamps, queue/device changes, and samples whose measured interval does not cover all source rendering. Never substitute the QuadView compositor timer, OpenXR predicted display period, a raw FPS counter, or CPU wait time for scene GPU time. Treat frame-generation/reprojection/present cadence as separate telemetry; do not use generated or repeated presentation frames as render samples. If a cap or CPU bottleneck prevents attributing a delay to GPU scene work, hold the current percentage rather than lowering resolution.

Use asymmetric, hysteretic steps with time-based evaluation windows—for example, consider a 2 percentage-point reduction after sustained over-budget evidence and a 1-point recovery after longer headroom. These are initial test values, not shipping defaults. Require valid, complete samples between writes and a settling window after each change. Clamp to the derived supported interval. Make at most one game-thread write at the start of a new draw, then freeze the chosen value in that draw’s snapshot for both DuoView passes or all four QuadView passes. Do not write once per constructor, family, eye, or render callback, and do not persist an automatic percentage every frame.

Respect existing CVar ownership. `CVarManager` already lists `r.ScreenPercentage`, supports a manually frozen value, and enforces frozen CVars from `on_pre_engine_tick`; the adaptive path must not race that behavior. Add a narrow read-only ownership query or lease API for this CVar. If the user has manually frozen it, a game/upscaler writer changes it, or the active upscaler cannot declare its valid dynamic range, refuse or stop adaptive control with a clear status. Capture the baseline only when taking ownership. On disable or mode exit, restore the baseline only if the live value still equals the controller’s last write; if another writer changed it, release ownership without overwriting that writer. Keep the feature disabled by default and avoid changing saved CVar configuration.

For NVIDIA DLSS Super Resolution, use the active plugin’s supported source-size bounds if it exposes them; NVIDIA’s Streamline guide documents optimal settings and min/max source sizes when dynamic resolution is supported. Do not infer capability from an NVIDIA GPU alone. DLSS Ray Reconstruction is an explicit incompatible case in NVIDIA’s current guide: it does not support DRS, and changing input resolution during rendering triggers denoiser reinitialization. Verify the exact STALKER 2 plugin/version and active modes before allowing adaptation; otherwise report the conflict and leave the controller off.

### 4. Measurement-gated memory and raster-cost experiments

After collecting baselines, identify whether the cost is GPU raster, post-processing, CPU submission, compositor, or memory pressure. If ID7 scene GPU time or VRAM is dominated by the four full-atlas resources and their UE histories, prototype a right-sized resource path in a separate experiment. Preserve view projections, source rectangles, eye FOV, gaze, and the accepted Build 40 crop geometry. Do not shrink or reinterpret projection bounds simply to reduce pixels. Compare target memory and GPU time on the same route; abandon the experiment if it changes framing, stereo depth, shadow behavior, or source/history correctness.

Optimize the compositor only if its own measured pass is a material share of total GPU time. Keep the production WARP image tests as a pixel-exact guard for separate eye sources, crop edges, formats, and encoded output. Do not use synthetic colors as evidence of in-game gamma or lighting parity.

## Implementation sequence and acceptance

For the first diagnostic increment, use the existing native delivery/retirement owners and add only bounded snapshots plus assertions that attach/execute/reset and pending/staged/fenced/ready transitions are reflected correctly; do not change lifetime policy. Keep it separate from future adaptive percentage work. For screen percentage, keep the portable control law in a new small header under `quadview/` with deterministic unit tests for valid/invalid samples, hysteresis, min/max clamping, one-change-per-draw, external writer takeover, baseline restore, and stale generation rejection. Wire one shared controller into the game-thread draw setup used by both ID6 and ID7, and carry the selected percentage in the frozen per-draw state. Extend the overlay generators and source-checkpoint tests so generated backend edits are reproducible; do not edit the generated `/workspace/scratch/8c6d683aba7f/backend` tree directly.

Acceptance requires Windows CI and the pinned DuoView regression suite; tests that prove all 2/4 views in one draw received the same percentage; an in-game log proving samples cover the correct source work and queue; and a same-scene before/after headset run with frame-time percentiles, effective screen percentage, image quality, FOV/gaze/stereo checks, compositor/reprojection statistics, and peak VRAM. Ship the adaptive feature disabled by default until that end-to-end evidence passes. Keep a single toggle to return to manual screen percentage and verify the conditional baseline restore path.
