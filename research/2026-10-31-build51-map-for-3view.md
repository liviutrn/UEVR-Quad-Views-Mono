# Build 51 source map and three-view stereo recommendation (2026-10-31)

**Scope:** ID7 Build 51 source commit [`f4e086c`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/commit/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77) and published DuoView **v186.2** source [`9152267`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/commit/915226735b03dc736028f01b93cb39a20efe81cb). This is a **research map, not a completed build**.

**Evidence labels:** **[MEASURED—source]** means independently inspected code/repository metadata, *not* timed gameplay. **[LIVIU—headset]** means Liviu's earlier headset observations, not a measurement reproduced here. **[REMEMBERED/ESTIMATED]** means prior discussion, proposed design, inferred mechanism, or unavailable quantitative evidence. No number below is claimed as benchmark-measured unless explicitly stated.

## Part A — history and unanswered measurements

**1. Build 40 versus Build 51.**

- **[LIVIU—headset]** Build 40 (`7486fc5`) eventually produced working binocular stereo, correct gaze tracking and FOV, and subjectively **good performance**, though startup could briefly black-screen. Its *indoor illumination was substantially brighter* than DuoView/Mono/native stereo; shadows or Lumen appeared missing or incorrect. Liviu also noticed a **left-eye context/periphery versus left-eye focus** shading difference. No exact Build 40 FPS was documented.
- **[MEASURED—source]** Build 40 is the accepted *four views in one render family* starting point. Build 46–51 changed delivery to **four engine renderer calls with one authenticated scene view/target in each**. Build 51 retains this path; see [dispatch patch](../quadview/apply_quadviews.py), roughly lines 1215–1290, and [BUILD46_FINDINGS_STATUS](../quadview/BUILD46_FINDINGS_STATUS.md). One render family does **not** mean one pixel/eye; these are different engine-dispatch architectures.
- **[LIVIU—headset]** Later Build 51 was reported to show true four-view stereo but with **very poor CPU-side performance and visible view-dependent lighting**. An earlier Build 51 source status was initially a *test candidate*, not a proof of headset function. Exact Build 51 FPS was not supplied in the available observations.
- **[REMEMBERED/ESTIMATED]** The proposed comparison **Mono ~40, quad ~25–30, three-view ~32–34 FPS** is a planning estimate/user work-order baseline, **not** a comparable measured three-mode benchmark. The exact Build 40 and Build 51 numbers remain **unknown**.

**2. Lighting/shadow differences and Native Stereo Fix.**

- **[LIVIU—headset]** Both categories were seen, but not always in the same test: (a) **fovea versus periphery within the left eye** in Build 40; (b) **left-eye views versus right-eye views** in later quad tests (left fovea/periphery reportedly brighter than right). Build 40's interior as a whole was brighter than other rendering modes, sometimes perceived as similarly incorrect in all its views.
- **[LIVIU—headset]** Effects described were **shadows, Lumen/indirect lighting, and overall brightness**. Specific UE buffers or exposure histograms were **not measured**, so an automatic-exposure cause remains a hypothesis, not a diagnosis.
- **[LIVIU—headset]** Stock Joey Native Stereo's second eye was less well shaded; **Native Stereo Fix improved secondary-eye shading, but did not make it perfect**. The newer ID7 four-singleton variant remained imperfect in-headset.
- **[MEASURED—source]** ID7 explicitly disables the normal two-eye `is_native_stereo_fix_enabled()` gate in [apply_quadviews.py](../quadview/apply_quadviews.py) (around line 207) **because it substitutes its own four-source Native-Fix-style dispatch**, with independent `FSceneViewState`, forced `eSSP_PRIMARY`, separate targets and frame/tail ownership. Thus it is false to infer that Build 51 simply omitted *all* Native Stereo Fix mechanisms. It is equally false to claim parity has been proven.

**3. Hands/weapon and MPC_FOV in Build 51.**

- **[REMEMBERED/ESTIMATED]** No Build 51-specific, controlled headset observation establishing whether **hands/weapon were correctly sized, doubled, or inconsistent in any view** was found. Do not import hand artifacts from the separate DIBR/DuoView tests into ID7 as evidence.
- **[MEASURED—source]** Build 51's source line is descended from the earlier v182 DuoView baseline. Its ID7 patches do **not** install the later `MPC_FOV` controller; `IsFOVEnabled=0` / `DepthScale=1` are **not evidenced as active in ID7**. The v186.2-specific controller resides in [apply_foreground_mpc_minimal.py](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/915226735b03dc736028f01b93cb39a20efe81cb/duoview/joey_stage1/apply_foreground_mpc_minimal.py) and is gated to DuoView ID6. An explicit ID7 port and test are needed.

**4. CPU profiling.**

- **[REMEMBERED/ESTIMATED]** No comparable `stat unit` **GameThread/RenderThread/RHI ms** captures or paired frametime logs for Mono, native stereo, and quad views were available. Subjective "CPU poor" is not a `stat unit` measurement. The ID7 `gpu_timing` option times its **D3D12 compositing pass**, not the Unreal four-render CPU cost.
- **[REMEMBERED/ESTIMATED]** Before quoting a three-view FPS gain, record a fixed indoor scene, matching game save, render scale, DLSS and settings, repeated steady-state 60-second captures, median/p95 **GT, RT, RHI, GPU and app frametimes** and headset frame pacing. Do not use just SteamVR's interpolated frame rate.

**5. Joey Native Stereo + Native Stereo Fix FPS.**

- **[REMEMBERED/ESTIMATED]** No defensible same-scene numerical FPS was found. Liviu reported better shading with the Fix and remaining shading imperfections, but not a matched performance measurement. **Unknown**, not zero and not 25–30 FPS.

**7. Four view request, stereo cameras, projections and roles.**

- **[MEASURED—source]** [`QuadViewViewDemand.hpp`](../quadview/QuadViewViewDemand.hpp) `desired_view_count` (lines 13–16) returns **4** only for active ID7 with ready hooks, otherwise **2**. [`apply_quadviews.py`](../quadview/apply_quadviews.py), around lines **1000–1023**, patches `FFakeStereoRenderingHook.cpp`'s desired count and view rectangles. [`QuadViewGeometry.hpp`](../quadview/QuadViewGeometry.hpp), `make_layout` (61–107), defines **0=L context, 1=R context, 2=L focus, 3=R focus**; `eye_for_view(i)=i&1`, `is_focus_view(i)=i>=2`.
- **[MEASURED—source]** [`apply_quadviews.py`](../quadview/apply_quadviews.py), around **1028–1073**, overrides double-precision `CalculateStereoViewOffset`: context 0/1 get their original left/right eye camera poses and capture those poses into `QuadViewProducer::context_camera`; focus 2/3 **reuse the matching eye's context camera**. Around **1076–1144** it patches `CalculateStereoProjectionMatrix`: context 0/1 retain respective OpenXR eye projections; focus 2/3 inherit same-eye projection and `apply_focus_crop`. Around **1147–1202** the view constructor sets `eSSP_PRIMARY`, clears view accumulation during construction, captures unique view state and validates the actual `FSceneViewInitOptions` matrix.
- **[REMEMBERED/ESTIMATED—3-view design]** Replace implicit parity roles with a named **`SharedContext, LeftFocus, RightFocus`** mapping. Request count **3**, not 4; build one full-FOV **center-head camera** (translation/rotation derived from the coherent head pose), with a **union frustum that covers both eye frusta**. Give the two focus views real left and right poses/cropped projections. Change `QuadViewProducer`'s exact four-view masks/arrays and [`QuadViewFamilyRouting.hpp`](../quadview/QuadViewFamilyRouting.hpp)'s quartet identity/dispatch accordingly. Do **not** map the centered view to `view_index & 1`: that would silently make it a left or right eye. A centered context projection **cannot** be treated as identical per-eye UVs; add per-eye direction/projection mapping at composition, accepting that step 1 has **no translation/depth reprojection**.

**8. Texture creation, ownership, publication and four-count contracts.**

- **[MEASURED—source]** [`apply_quadviews.py`](../quadview/apply_quadviews.py), ~**661–934**, patches `VRRenderTargetManager_Base`: it makes **four** `KismetRenderingLibrary::CreateRenderTarget2D` textures of full **double-wide atlas extents** (although each rendered view's rectangle is small), captures UE `FRenderTarget`/`FRHITexture`/native `ID3D12Resource`, installs/validates target hooks and publishes `QuadViewNativeTargetSetSnapshot` with four target owners. These are independent scene outputs, not simply four shader samples of one original atlas.
- **[MEASURED—source]** The new [`apply_quadview_target_lifetime.py`](../quadview/apply_quadview_target_lifetime.py) adds per-target **world actor → noncapturing `USceneCaptureComponent2D` → `TextureTarget` UPROPERTY** retention (lines 19–46, 95–131), identity and destruction checks, and GT disposal only after CPU/GPU leases retire. [`apply_quadview_present_setup.py`](../quadview/apply_quadview_present_setup.py) separates presentation setup fences from complete engine-mode retirement. These scripts are **not in the checked workflow sequence** (see #6).
- **[MEASURED—source]** Original view-family dispatch and later singleton calls are in `apply_quadviews.py` ~**1217–1290**, refined by [`apply_quadview_native_delivery.py`](../quadview/apply_quadview_native_delivery.py), [`apply_quadview_role_frames.py`](../quadview/apply_quadview_role_frames.py). GT registers the family and freezes a packet **before Unreal copies the views**; RT matches exact role frame/scene/target; Slate/RHI tail completion and per-physical-target content stamps gate publication. See [`QuadViewDelivery.hpp`](../quadview/QuadViewDelivery.hpp), [`QuadViewNativeDelivery.hpp`](../quadview/QuadViewNativeDelivery.hpp).
- **[MEASURED—source]** Hard four-count assumptions include: `QuadViewViewDemand` (4), `QuadViewGeometry::Layout.views[4]`, `QuadViewProducer::Snapshot.views/projections[4]` and **`0x0f`** completion masks, `QuadViewFamilyRouting` four-view matching, `QuadViewNativeTargets::valid_native_target_quartet` **requires four unique target identities**, `QuadViewNativeDelivery` **four targets/role frames** and `0x0f` hooked masks, four physical source owners, four-stamp coherence, compositor four SRVs and all singleton loops. Do not merely change the requested count to 3: publication will otherwise never complete.
- **[REMEMBERED/ESTIMATED—3-view design]** Prefer **three physical targets + three distinct Unreal histories + three completion/stamp identities**, while keeping four **logical SRVs** in the first shader prototype by binding shared context to both t0 and t1. A duplicate *descriptor* is fine; passing duplicate **physical targets into the original four-target identity validator** is not. Retain GT/RHI/fence discipline rather than bypassing it for an FPS test.

**9. Composition path and change for a shared context.**

- **[MEASURED—source]** [`QuadViewComposite.hlsl`](../quadview/QuadViewComposite.hlsl) `CompositePixel` (roughly lines **122–164**) selects eye by double-wide output X, uses **t0/t1** for eye-specific context, **t2/t3** for eye focus, computes eye-specific crop/feather and blends. Diagnostic modes show context, focus or role colors. Focus-only **Glamarye** is already fused in the shader. [`QuadViewD3D12.hpp`](../quadview/QuadViewD3D12.hpp) `Compositor::record_sources` (184–292) sets four SRV descriptors and GPU ownership, then outputs a double-wide stereo texture for ordinary OpenXR left/right submission.
- **[MEASURED—source]** `record_sources` **permits duplicated source pointers** and deduplicates D3D12 resource barriers. Thus the low-risk composer bridge can bind **`{shared_context, shared_context, left_focus, right_focus}`**, keep its four descriptors, and alter only context sampling UVs to project the **same center-camera image** into each eye's angular coordinates.
- **[REMEMBERED/ESTIMATED—optical limitation]** A shared center image without depth cannot correctly represent **per-eye translation parallax, foreground occlusion or disocclusion**. Even if its center projection is correct, naive identical UV sampling causes scale/position seams at the real-stereo focus boundary. Step 1 must explicitly measure seam behavior in a near-hand/weapon scene versus a distant outdoor scene; no synthesis in this phase is deliberate, but it does **not** imply correct stereo periphery.

**10. PSVR2 gaze and placement.**

- **[MEASURED—source]** ID7 uses [`QuadViewPSVR2Gaze.hpp`](../quadview/QuadViewPSVR2Gaze.hpp), its own reader wrapping the **same PSVR2 Toolkit CAPI DLL and same calibrated gaze ray** logic as [`DuoViewPSVR2Gaze.hpp`](../duoview/DuoViewPSVR2Gaze.hpp). `VR::quadview_begin_frame` in [`apply_quadviews.py`](../quadview/apply_quadviews.py) ~**351–530** samples once per frozen draw, projects the head-relative ray to **both eye UVs**, and uses two [`DuoViewCropStability.hpp`](../duoview/DuoViewCropStability.hpp) state machines for quantized, guarded crops. It does **not** reuse DuoView ID6's exact `read_uv` call/mono projection; it reuses the underlying PSVR2/calibration/recovery design.
- **[REMEMBERED/ESTIMATED—3-view design]** Keep the **two independent gaze-cropped focus positions** and per-eye OpenXR pose; only the far-field context becomes center-mono. Do not center the *focus* cameras.

- **[MEASURED—source]** Published [v186.2 release notes](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/main/RELEASE_NOTES_V1862.md) identify source `9152267` / Actions #206, a **different and diverged source line** (GitHub compare: 52 commits ahead, 77 behind). Build 51 **already includes its own fused focus-only Glamarye filter** and inherits **DuoView crop stabilization logic**, so those two should **not** be blindly ported a second time.

When a load breaks lookup, the proven workaround is **manual Reapply**, possibly triggered via a hotkey; this is explicit in its release notes. The new #206 hotkeys were source/CI-tested, while the #205 manual path was headset-tested.
- **[REMEMBERED/ESTIMATED—port priority]** For a **true-stereo ID7**, port **MPC_FOV first** (including manual reapply) to keep near-field weapon sizing, then any desired **XYZ head scaling** with strict head-center/IPD checks. Port hotkeys later. **Do not automatically carry Mono HUD convergence or Mono eye alignment** into true stereo: their mono-only optical assumptions may create the wrong stereo geometry. Retain QuadView's own Glamarye and crop code; compare output rather than merge duplicate implementations.

## Part C — risks, decision and implementation order

1. **[REMEMBERED/ESTIMATED—highest risk: architecture]** The quartet ledger, frame-family router, `PRIMARY` construction, native target ownership, RHI tail and physical-content proof all encode **exactly four**. A simplistic 4→3 edit produces black output, stale packets or unsafe engine dispatch. Use a named three-role table and update the **entire producer→GT→RT→RHI→compositor invariant**; add negative tests for missing/duplicate context, role reassignment and mode switching.
2. **[REMEMBERED/ESTIMATED—quality]** A center mono periphery has **no baseline parallax**, and its FOV/UV cannot equal both eyes at once. The focus/periphery seam may be more distracting than modest frame savings, particularly on weapons, hands and nearby vertical edges. Start with **plain mono and a visible feather**, but compare distant and near content and record eye-specific seam failures rather than promising acceptable stereo.
3. **[REMEMBERED/ESTIMATED—performance/lighting]** Three engine renderer calls may remain **RT/GT-limited**, and the third independent camera/history may still diverge in Lumen, shadows, auto exposure or temporal upscaling. Expected ~32–34 FPS is **unmeasured**. Need `stat unit` and consistent same-scene captures; do not call a build a performance success just because pixel count decreases.

**Recommendation:**

- **[REMEMBERED/ESTIMATED]** **Start from the Build 51 ID7 renderer architecture, not by porting 3-view into v186.2's mono ID6 architecture.** Build 51 already has the crucial **independent per-eye scene cameras, scene states, physical target ownership and stereo OpenXR compositor**. Starting from v186.2 would require inventing that rendering path again and risks corrupting a working mono line. Keep v186.2 as a **read-only feature reference** and selectively port required MPC/headscale functions after 3-view correctness.
- **[MEASURED—source / immediate gate]** **First fix the reproduction gap**: wire every intended Build48–51 overlay into the actual Windows workflow, then verify the generated backend and its checksum/source manifest, commit SHA and artifacts. The exact `f4e086c` CI binary was **not verified** by this audit. A local code review cannot substitute for a Windows build using the restricted UESDK.
- **[REMEMBERED/ESTIMATED—test sequence]** (1) reproducible 4-view Build51-equivalent baseline with known headset output; (2) 3-view physical targets, named role mapping and three-entry exact completion; (3) center pose + stereo focus projections + angle-aware UV sharing through duplicated context descriptors; (4) repeatable cold startup, ID7↔ID6↔ID0, save/load and 10-minute motion tests; (5) same-scene FPS/CPU/GPU/lighting and near-seam A/B; (6) targeted MPC_FOV manual recovery port; (7) only then optional UI/headscale refinements.

**Validation boundary:** **[MEASURED—source]** Source files, commit/branch metadata, workflow/pin values and the v186.2 release tree were inspected. **[REMEMBERED/ESTIMATED]** No Windows C++ compilation, UESDK integration build, GPU capture, fresh headset session or independent second-model review was run for this research-only commit. Do not mark build correctness, lighting parity, seam quality or 32–34 FPS green.
